# Состояние проекта и направления рефакторинга

Дата: 4 ноября 2026 года. Аудит текущей локальной версии проекта.

## Вывод

Модульная основа пригодна для дальнейшего развития: React Query управляет серверными данными, Zustand — состоянием рабочих областей, медицинские модули используют общие API/DTO/query-хуки. Замена стека и масштабное переписывание не обоснованы.

Первое необходимое действие — восстановить согласованность DTO, представлений и проверок. Затем основной выигрыш даст последовательное устранение дублирования MedView/RControl. Точечные исправления состояния, запросов и токенов можно выполнять отдельными небольшими изменениями.

## Что проверено

- Изучены структура приложения, маршрутизация, сессия, общий транспорт, query-хуки, фильтры, stores, примеры категорий MedView/RControl, Admin, экран документов HealthTrack и стили.
- В `src` 638 файлов; MedView — 188, RControl — 147. Это число файлов всех типов, а не число компонентов.
- Для 126 файлов MedView найдены соответствующие пути RControl. В 55 парах содержимое совпадает после нормализации названий модулей и переводов строк. Подсчёт включает TS/TSX и SCSS, не является измерением процента дублирования всего проекта.
- `npm.cmd run build` завершился ошибкой на TypeScript, до Vite. Отдельный `tsc -b --pretty false` подтвердил 49 ошибок в 19 файлах.
- `npm.cmd run lint` завершился успешно: два предупреждения о зависимостях hooks в `HTDocumentsTab.tsx`.
- Запущены пять наборов Node-тестов: `admin-access`, `admin-contract`, `admin-management`, `medview-oncology`, `rcontrol-selection`. Из 34 тестов прошли 33, один завершился ошибкой.
- Браузерные сценарии, реальные API и production bundle в рамках аудита не проверялись. Производительность и визуальные регрессии не измерялись.
- Код приложения не изменялся. Единственное добавление — этот документ.

## Сильные стороны, которые стоит сохранить

- Общий слой медицинских контрактов и запросов уже существует; не нужно начинать объединение модулей с нуля.
- В RControl есть поведенческие тесты каскадного сброса выбора при смене источника, организации, периода и родительских записей.
- Admin разделён на API services, query/mutation hooks, модели форм и UI. Используются AbortSignal и адресная инвалидация кэша.
- Восстановление сессии учитывает отмену запроса и смену токена. Обработчик 401 защищён от очистки новой сессии старым запросом.
- Есть общие `DataState`, `resolveDataState`, элементы карточек и таблиц, дизайн-токены и изолированная демосреда Admin.

## Направления по приоритету

### P0. Согласовать DTO, UI и демоданные

**Основание.** Сборка заблокирована 49 ошибками типов. Например, `MedicalCaseDetailsDto` содержит `medicalProfileCode` / `medicalProfileName`, а MedView обращается к `medicalProfile`. Аналогичные расхождения есть в завершённых случаях, услугах и диагностике. Демоданные обоих модулей также не соответствуют текущим типам. Ошибки затрагивают рабочие компоненты, поэтому исключение preview из проверки не решит проблему.

**Действия.** Сверить спорные поля с актуальным контрактом backend; затем согласовать UI и фикстуры по одной предметной области. Уточнить отображение кода и названия при `null`, не подменяя контракт предположениями и не ослабляя TypeScript.

**Готово, когда:** production build проходит, реальные ответы соответствуют выбранным типам, карточки корректно показывают код/название и отсутствие значения. Проверка backend — отдельная часть работы; текущий аудит устанавливает только внутреннее расхождение фронтенда.

### P0. Сделать проверки воспроизводимыми

**Основание.** В `package.json` есть build/lint, но нет команды запуска тестов. Тест `UI permissions follow the API's permission claim, not role names` падает: `readTokenClaims` возвращает дополнительные `organizationCode: null` и `organizationType: null`, которых нет в ожидаемом объекте. Это конкретное расхождение ожиданий; оно само по себе не доказывает ошибку проверки прав.

**Действия.** После проверки ожидаемого поведения актуализировать тест. Добавить команды для Node-тестов и выбранных browser smoke-сценариев. Зафиксировать требования к Node/Chrome и порядок проверок; подключать CI в рамках используемого в команде процесса. Не вводить новый тестовый фреймворк без необходимости.

**Готово, когда:** разработчик может одной документированной последовательностью запустить lint, build и тесты; утверждения проверяют поведение и контракт.

### P1. Объединять представления MedView/RControl по одной категории

**Основание.** Подтверждены 55 совпадающих пар файлов. Примеры: `ClinicalGroupCardBody`, заголовки карточек, `TreatmentCoefficientsListBody`, таблицы дефектов и SCSS. При этом контейнеры категорий привязаны к разным stores и рабочим сценариям.

**Действия.** Начать с одной простой категории, например пациента. Оставить в модулях получение контекста выбора, работу со store и orchestration запросов. Вынести одинаковые представления с явными props данных/состояния/действий в общий предметный участок рядом с существующим `invoiceStructure`. Учитывать уникальные DOM id. После проверки подхода переносить следующие категории; сложную онкологию оставить на более поздний шаг.

**Готово, когда:** выбранная категория имеет одно общее представление, используется обоими модулями и демосценариями, различия поведения остаются явными. Не создавать один универсальный workspace с множеством флагов. Размещение общих предметных компонентов и границы их ответственности согласовать как архитектурное решение.

### P1. Зафиксировать время жизни фильтров и правила сброса выбора

**Основание.** В MedView draft находится в локальном `useState` у `MedViewFiltersRoot`, а applied filters — в глобальном Zustand store. После размонтирования и возврата draft создаётся заново, применённые условия сохраняются. Пользователь может видеть поля, не соответствующие выдаче. Сброс workspace перед применением фильтров выполняется обработчиком UI, а не действием модели.

**Действия.** Выбрать продуктовую семантику возврата на страницу: сохранять draft вместе с applied либо явно сбрасывать оба. Свести связанные операции применения/сброса к одному месту. Проверить смену источника, фильтров, страницы и родительского выбора. Использовать селекторы Zustand там, где компоненту нужна отдельная часть состояния; приоритет оптимизации рендеров подтверждать профилированием.

**Готово, когда:** видимые условия соответствуют выдаче, дочерний выбор сбрасывается предсказуемо, переходы между модулями покрыты регрессиями. Общий store для двух модулей не требуется.

### P1. Выровнять отмену запросов, время ожидания и кэш

**Основание.** Общие медицинские query-хуки и API-функции, например `usePatientQuery` / `getPatient`, не передают AbortSignal. Admin уже использует отмену. Общий Axios timeout равен 20 минутам, включая обычное чтение; импорт HealthTrack задаёт такой timeout отдельно. `useAutocompleteFilterOptionsQuery` задаёт бесконечные `staleTime` и `gcTime` для ключей с поисковой строкой.

**Действия.** Провести signal от React Query до Axios в используемых цепочках запросов. Согласовать timeout обычного чтения отдельно от длительного импорта. Для автодополнения определить ограниченный срок кэша; сначала проверить фактическое использование хука, поскольку прямых потребителей при поиске не найдено. Политику retry для 401/403 и серверных ошибок сделать явной, используя уже имеющийся пример Admin. Устранять повторение проверки `ResultResponse` только при устойчивой одинаковой семантике.

**Готово, когда:** ненужное чтение отменяется при смене контекста, ошибка доступа не повторяется автоматически, долгое выполнение остаётся доступно операциям, которым оно требуется. Backend routes и DTO не менять.

### P2. Согласовать токены и форматирование значений

**Основание.** Найдено 15 ссылок на неопределённый `--fs-body1`; в typography определены `--fs-body` и `--fs-body2`. Существуют старые семантические токены и новые `--mt-*`. `--text-primary` уже имеет alias, поэтому прежнее замечание о его отсутствии устарело. `--module-accent` и `--module-cover` задаются inline в `ModuleCard` и не являются пропущенными глобальными токенами.

Общий `formatDate` и локальные функции дат имеют разную обработку некорректных значений и часовых поясов. В категориях повторяются функции форматирования.

**Действия.** Сначала исправить неопределённую типографику. Затем описать назначение двух семейств токенов и сводить одинаковые значения через aliases, сохраняя текущий вид. Разделять календарную дату и момент времени при объединении форматтеров; использовать существующие тесты невозможных дат и смещений часового пояса.

**Готово, когда:** нет необъявленных используемых токенов, форматирование имеет явную семантику, глобальные изменения проверены на MedView, RControl, главной, login, Admin и доступном экране HealthTrack.

### P2. Уменьшить обратные зависимости общего слоя

**Основание.** `shared/api/references/getFilterOptions.ts` и общие select/autocomplete импортируют `FilterOption` из внутренней модели MedView. Общий `apiClient` импортирует auth-store; auth-store обращается к общему query client.

**Действия.** Первым небольшим изменением перенести действительно общий `FilterOption` в общий слой и обновить импорты. Зависимость транспорта от auth рассматривать отдельно: при необходимости согласовать настройку транспорта на уровне приложения, сохранив обработку старых 401 и очистку кэша. Не создавать service locator или DI-систему ради этого изменения.

**Готово, когда:** общие поля и справочники не зависят от внутренностей MedView; изменения сессии сохраняют существующие гарантии.

### P3. Отдельная очередь HealthTrack, загрузки модулей и документации

**HealthTrack.** В `HTDocumentsTab` сосредоточены фильтры, пагинация, выбор, команды проверки/удаления, уведомления и открытие деталей. Есть файлы UI более 400 строк. Разделять их стоит по обязанностям: модель выбора/команд, композиция страницы, представление. Два lint warning связаны с `pagedResult?.items ?? []`, создающим новый массив при отсутствии данных; это небольшое локальное исправление. Предыдущий план исключал HealthTrack из основной очереди: возвращение к нему требует отдельного выбора приоритета, а не автоматического расширения текущих работ.

**Загрузка модулей.** Основные страницы статически импортируются в `src/app/main.tsx`; глобальный provider уведомлений принадлежит HealthTrack. После восстановления сборки измерить bundle и загрузку страницы, затем оценить `lazy` на уровне маршрутов и перенос действительно общего provider. Сейчас численных оснований обещать ускорение нет.

**Документация.** `README.md` пуст. План M01–M09 от октября частично отстаёт от реализации: Admin и общая сессия уже существуют. Добавить краткое описание запуска, proxy/API, тестов и структуры. Обновлять статусы плана по проверенным результатам; архивные дефекты не считать автоматически актуальными.

## Предлагаемая последовательность небольших изменений

1. Согласовать контракт и UI медицинских случаев; отдельно обновить соответствующие demo fixtures.
2. Довести остальные DTO/фикстуры до проходящей сборки, актуализировать JWT-тест и команды проверок.
3. Закрепить поведение возврата к фильтрам MedView и каскадного сброса выбора.
4. Согласовать и внедрить общее представление одной категории MedView/RControl, проверить оба сценария.
5. Переносить остальные категории отдельными изменениями; для каждой обновлять связанные демоданные и проверки.
6. Независимыми изменениями исправить токен, общие типы справочников и отмену запросов. Оценивать bundle после успешной сборки.

Для каждой задачи критерий завершения — сохранённое поведение, проходящие релевантные проверки и отсутствие новых обходов типов. Изменения API-контрактов, структуры общих предметных компонентов и семантики сохранения фильтров требуют согласования. Новые зависимости для перечисленных направлений пока не нужны.
