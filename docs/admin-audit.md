# Admin: фактическая структура и подготовка редизайна

## Разделы и сценарии

| Маршрут | Страница | Функции |
| --- | --- | --- |
| `/admin/users` | `AdminUsers` | Список учётных записей, создание, открытие диалога пользователя |
| `/admin/roles` | `AdminAccessCatalog kind="role"` | Список, создание роли, просмотр и замена набора разрешений |
| `/admin/permissions` | `AdminAccessCatalog kind="permission"` | Список кодов/названий/описаний, создание разрешения |

У всех списков есть обновление и loading / empty / error, но нет серверной пагинации, сортировки или поиска. Autocomplete используется в формах для организаций, ролей и разрешений. Удаление пользователей/ролей/разрешений и редактирование названий ролей/разрешений не реализованы.

`UserDetailsDialog` объединяет `UserProfileForm` (имя, фамилия, отчество, телефон, email, дата рождения), `UserRolesPanel` и `UserStatusPanel`. Идентификаторы пользователя и организации показаны отдельно. Логин и организация не входят в PATCH профиля. Создание дополнительно требует логин, пароль и организацию из справочника. Данные отправляются через существующие валидаторы и сборщики запросов.

Профиль, роли и статус учитывают dirty/busy соседних панелей. Есть отмена, подтверждение закрытия несохранённых изменений и `beforeunload`. Самоотключение завершает сессию; замена собственных ролей требует нового входа. Текущий статус пользователя отсутствует в DTO: панель прямо сообщает об этом и предлагает команды «Активировать» / «Отключить». Демо подтверждает эти команды локально, не придумывая поле статуса.

`RoleDetailsDialog` загружает роль, назначенные разрешения и доступный справочник отдельно. Замена набора требует чтения назначений, справочника и права изменения. Пустой набор допустим. После изменения интерфейс предупреждает о необходимости повторного входа пользователей.

## Данные и доступ

`adminUsersService` и `adminAccessService` используют Identity API `/identity/admin/*`. `useAdminUsersQueries` и `useAdminAccessQueries` хранят серверное состояние в React Query с пространством `admin`, сигналами отмены и адресной инвалидацией. Локальные draft/validation/dialog state находятся в компонентах. Отдельного Admin store нет.

DTO: `AdminUser = AuthUser`, `AdminOrganization`, `AdminRole`, `AdminPermission`, запросы создания и частичного изменения пользователя. Никаких медицинских данных в Admin нет. Пароль используется только при создании; mutation cache имеет `gcTime: 0`.

Доступ определяется permission claims JWT через `adminPermissions`, а не названием роли. Внешний `AuthSession` восстанавливает реальную сессию; `RequirePermission` перенаправляет гостя на login и показывает запрет при недостаточных правах. Право создания без права чтения открывает создание без списка. Кнопки и панели имеют дополнительные проверки своих permissions. Backend остаётся источником окончательного решения о доступе.

## Визуальный аудит и порядок переработки

1. **Оболочка и навигация:** `AdminNavigation`, заголовки `AdminUsers` / `AdminAccessCatalog`. Утвердить общую белую секцию, компактные действия и поведение навигации.
2. **Список пользователей:** наиболее насыщенная таблица, затем роли и разрешения. Сохранить фактические колонки; применить opt-in `mt-table-*`, локальную прокрутку и общий ритм отступов.
3. **Пользователь:** `UserDetailsDialog`, `UserProfileForm`, `UserRolesPanel`, `UserStatusPanel`, `CreateUserDialog`. Согласовать мягкие внутренние панели, плотность форм и сохранность предупреждений опасных/self-действий.
4. **Роли и разрешения:** `RoleDetailsDialog`, `CreateAccessDialog`; унифицировать Autocomplete, выбранные элементы, действия и dirty-состояния.
5. **Проверка всех состояний и узких контейнеров**, включая длинные имена/коды, формы ошибок и подтверждения закрытия.

Сейчас `styles.module.scss` пользователей использует старые `--space-*`, рамки, тени и глобальный `CardField`. `access.module.scss` уже применяет `--mt-*`, но имеет отдельные правила таблиц и форм. Возникают различия плотности, отступов, кнопок и оболочек диалогов. `RequirePermission` использует текст запрета про пользователей даже для других каталогов — отдельный будущий UX-polish.

Референсы: актуальные секции и таблицы Workspace MedView/RControl, категории «Пациент» и «Детали случая», shared `PageContainer`, токены `medtools.design.tokens.scss` и opt-in таблицы `app/styles/table.scss`. Переносится визуальный язык, не медицинская композиция. На этом этапе эти стили и текущий Admin не перерабатываются.

## Демосреда

Запуск: `npm run dev`, затем `/admin?demoWorkspace=1`. Внутри работают настоящие три страницы Admin с их исходными UI, hooks, validators и диалогами. Панель сверху переключает данные, загрузку (5 секунд), пустые списки, ошибку чтения и ошибку сохранения. Есть вымышленные пользователи с частично пустыми полями, роли, permissions и организации; все email принадлежат `example.invalid`.

Стенд использует отдельный dev-only HTML entry point в iframe и существующие `MemoryRouter` / `QueryClientProvider`. Это изолирует global auth-store, query/mutation cache и Axios transport от основной вкладки. Основная сессия не меняется. В этой памяти создаются/редактируются только тестовые записи; неизвестные запросы блокируются, HTTP fallback отсутствует. После перезагрузки всё сбрасывается. Переключение внутренних разделов не меняет адрес родительской страницы.

Обычные маршруты остаются внутри `AuthSession` и `RequirePermission`. Только dev-ветка `/admin` расположена отдельно, чтобы сохранённый токен не запускал реальное восстановление сессии перед показом стенда. Production не импортирует демокомпонент и перенаправляет `/admin` на обычный защищённый `/admin/users`. В production-сборку не входят demo entry point, фикстуры и локальный transport.

Ограничения: iframe — изолированный экран разработки с собственной прокруткой; это не проект будущего layout Admin. Локальный транспорт не воспроизводит серверные транзакции, конкуренцию, все правила Identity API и реальные эффекты смены статуса. Реальную авторизацию и backend необходимо проверять отдельно.
